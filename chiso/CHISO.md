# 地相（CHISO）── 統合ドキュメント

> その土地の地形は、どんな産業を養えるのか。
> そして今、そこで何が詰まっているのか。

本書は3部構成。**第I部 目的**（なぜ作るのか）、**第II部 要件定義**（何を作るのか）、**第III部 作業指針**（どう作るのか）。
Claude Code に渡す場合は、本書をリポジトリ直下に `CHISO.md` として置き、「CHISO.md を読んでから着手して」と指示すれば足りる。

---

# 第I部　目的とナラティブ

## 1. 出発点にある確信

日本の国土の約7割は山地・丘陵地で、森林率は67%ある。平地は限られ、水は高いところから低いところへ流れ、雪は北と日本海側に降り、湯は火山帯に湧く。この配置は千年変わっていないし、これから千年も変わらない。

一方で、企業は消える。人口は動く。政策は変わる。産業は栄えて衰える。

つまり**地形だけが定数で、あとは全部変数**だ。長い時間軸で資本を張る者にとって、これほど信頼できる観測対象は他にない。

そして、移せないものだけが外から人と金を呼ぶ。工場は海外に移せる。ブランドも移せる。だが湯は移せない。山も、海も、雪も、水も移せない。**移せないものの上に建った事業だけが、構造的に競合を持たない。**

---

## 2. 解きたい問題

日本には二つのことが同時に起きている。

**ひとつ目：終わりの洪水**
空き家は2023年で900万戸、空き家率13.8%はいずれも過去最高で、うち賃貸・売却・別荘を除いた放置空き家だけで385万戸ある。休廃業は年6.7万件を超え、所有者不明土地は約410万haと推計されている。後継者のいない事業が、毎日どこかで静かに幕を閉じている。

**ふたつ目：見立ての不在**
その一件一件について、「この事業は畳むべきなのか、蘇るのか」を判定する共通のものさしが存在しない。判断しているのは、地元の勘、金融機関の担保評価、そして相続人の疲弊だ。土地が持つ本来の適性と、その上に乗っている事業が噛み合っているかを問う視点は、どこにもない。

だから、蘇るはずのものが畳まれ、無理筋のものに補助金が入る。

---

## 3. なぜ既存のやり方では届かないのか

- **不動産ポータル**は駅距離・面積・価格・用途地域で土地を見る。地形は検索条件にない
- **地方創生コンサル**は成功事例の横展開から入る。「隣の県で当たったから、うちでも」は地形を見ていない
- **金融機関**は過去の財務と担保価値を見る。土地の潜在適性は評価軸にない
- **PE・VC**はEBITDAとマルチプルを見る。そもそも小さすぎて視界に入らない

誰も地形から産業を読んでいない。読む道具がないからだ。

---

## 4. 何を作るのか

**地形データと制度データと産業データを重ね、メッシュ／市町村単位で「この土地が養える産業」と「今そこで詰まっているもの」を並べて見せる分析基盤。**

作らないものを先に書く。

- 「この土地を買うべきだ」という推奨は出さない
- 資産価値の上昇見込み、開発可否、安全性についての断定は出さない
- 複数の軸を合成した総合スコアは持たない

理由は単純で、**推定を断定として見せた瞬間、これは占いか、悪質な土地商法と区別がつかなくなる**からだ。地形から演繹した産業適性は、あくまで仮説にすぎない。仮説は仮説として、証拠は証拠として、法規制は法規制として、別々の層に分けて出す。この規律だけは仕様として固定する。

---

## 5. 誰のためのものか

**第一の利用者は、作者自身。**

「地形に合った小さな事業を一社見つけて、週末だけ入り込んで蘇らせたい」という自分の要求に、答えられる道具がなかった。だからまず自分のために作る。それ以外の用途は、作ったあとで考える。

想定される二次的な利用者は、事業承継の現場にいる人、地域金融、自治体、そして同じことをやりたい誰か。ただしMVP段階では意識しない。

---

## 6. どう使われるのか（作者自身の使い方）

1. 地相で「地形が示唆する産業」と「詰まりの兆候」が重なる区域を絞る
2. その区域に実際に行く。泊まる、食べる、歩く、話す
3. 一社を見つけ、週末だけ関わる。会社の源流に遡って物語を組み直し、外の客に接続する
4. **当たったか外れたかを記録して、地相に戻す**

4が最も重要になる。地形から演繹した仮説と、現地で起きた事実の差分。これは公開データではなく、歩いた者にしか貯まらない。判定の精度は、この差分の蓄積量に比例する。

---

## 7. 長い時間軸での位置づけ

このツールは目的ではなく、探索を自走させるための装置だ。

- **短期**：一社目を見つける。自分の判定軸が当たるかを確かめる
- **中期**：当たり外れの記録が貯まり、判定が属人的な勘から言語化された型になる
- **長期**：型が他人に渡せる形になれば、それは投資先を選ぶ基準であり、同時に人を育てる教材になる

事業を見つけるには5年から10年かかる。その長い探索を、勘と偶然だけに任せない。地形という定数を頼りに、狙って歩く。

---

## 8. 名前について

**地相**——土地の相を読むこと。人相・家相と同じ系列の古い語だが、ここでは占いの意味では使わない。

土地には来歴がある。会社にも来歴がある。どちらも、その源流に遡って読み直したとき初めて、本来の姿が見えてくる。会社の源流を読むのがコーポレートブランディングなら、土地の源流を読むのが地相だ。同じ作法を、対象を変えて適用しているにすぎない。

# 第II部　要件定義 v0.1

作成日：2026年8月10日 ／ 想定実装：Claude Code ／ 前提：第I部

---

## 0. 一行の定義

**公開されている地形・制度・産業・静脈データを重ね、地域単位で「地形が養える産業」と「今そこで詰まっているもの」を、層を分けたまま並べて見せる分析基盤。**

---

## 1. スコープ

### 1.1 MVP（v0.1）でやること

| 項目 | 内容 |
|---|---|
| 対象地域 | **1県のみ**（初期候補：長野県 or 大分県 or 山形県） |
| 空間単位 | 市区町村単位 ＋ 1kmメッシュ（地形指標はメッシュ、統計は市区町村） |
| 産業候補 | **6業種に限定**：温泉宿／発酵／林業・木工／果樹／水産加工／山岳観光・トレイル |
| 出力 | GeoJSON＋CSV、およびブラウザで見る地図ビューア（静的HTML） |
| 実行形態 | ローカルCLI（`chiso` コマンド）。サーバ運用は範囲外 |

### 1.2 MVPでやらないこと

- 全国展開 / 地番・筆単位の判定 / 総合スコアの算出・ランキングの断定
- 資産価値、値上がり見込み、開発可否、安全性の判定
- ユーザー登録、課金、API公開

---

## 2. 根幹の設計原則（変更不可）

### 原則1：三層を混ぜない
すべてのデータは `ESTIMATE` / `ACTUAL` / `LEGAL` /（v0.2で）`FIELD` のいずれかの層に必ず属する。異なる層の値を掛け合わせて単一の数値にすることを禁じる。全ての指標レコードは `layer` 属性を必須で持つ。

### 原則2：合成した総合点を持たない
軸ごとの素の指標のまま保持し、出力する。重み付けはビューア側のUIでユーザーが動かせるが、重み付けの結果はデータに保存しない。

### 原則3：断定を出力しない
「買うべき」「有望」「安全」といった語をシステムの出力文言に使わない。出力するのは指標値と、その指標が何に基づくかだけ。

### 原則4：できないことを先に書く
各指標には `limitations` フィールドを必須で持たせ、ビューアで必ず表示する。

---

## 3. データソース

`data/SOURCES.md` を参照。すべて公開データ。取得方法とライセンスを記録する。
（地形＝推定層の原料、制度＝法的層、産業＝現況層、静脈＝詰まりの兆候、接続＝外貨動線）

---

## 4. 産業適性ルール（v0.1の中核）

6業種それぞれについて、地形指標から適性を演繹する規則を人が書く。機械学習は使わない。
規則は `rules/*.yaml` に外部ファイルとして保持し、コードから分離する。

---

## 5. 機能要件

- **F-01 `chiso fetch`** — 対象県のソースを取得し `data/raw/` に保存。`data/SOURCES.md` に追記。`--force` で再取得。
- **F-02 `chiso terrain`** — DEMから傾斜・斜面方位・起伏量・谷底/尾根・集水面積を1kmメッシュで算出 → `data/derived/terrain_{pref}.parquet`
- **F-03 `chiso assess`** — `rules/*.yaml` を読みメッシュごとに業種別適性を層ごとに独立して算出（合成しない）→ `data/derived/assessment_{pref}.parquet`
- **F-04 `chiso stagnation`** — 空き家率・事業所減少率・高齢化率から市区町村単位の詰まり指標（合成せず並べる）
- **F-05 `chiso export`** — GeoJSON + CSV を `output/` に生成。各指標に `layer` と `limitations` を必ず含める
- **F-06 `chiso serve` / 静的HTML** — MapLibre GL JS。層ごとに色/線種を変え、切替トグル。重み調整スライダー可（結果は保存しない）。`limitations` を常時表示
- **F-07 現地記録（v0.2）** — `field/` にMarkdownで蓄積、観測層としてプロット

---

## 6. 非機能要件

Python 3.11+、ローカル実行。1県フルパイプライン30分以内。再現性（乱数を使わない）。説明可能性（どの入力とどの規則から導かれたか追跡可能）。生データはリポジトリに含めない。

---

```

├── CHISO.md / CLAUDE.md
├── rules/            産業適性ルール（YAML、人が書く）
├── src/chiso/        cli / fetch / terrain / assess / stagnation / export

├── field/            現地記録（v0.2）

```

---

## 8. 実装フェーズ

P0 骨格 → P1 地形指標 → **P2 温泉宿1業種が地図に出る（最優先）** → P3 法的層+現況層 → P4 残り5業種 → P5 詰まり指標 → P6 現地記録（v0.2）

---

## 9. 受け入れ基準（MVP）

1. 1県について6業種の推定層が1kmメッシュで地図表示される
2. 推定/現況/法的層が視覚的に区別され切替できる
3. 合成された総合スコアがどこにも存在しない
4. すべての指標に `limitations` が付随し画面に表示される
5. 「買うべき」「有望」等の断定語が出力に含まれない
6. データ取得から出力までコマンド一本で再現できる
7. **作者が地図を見て、実際に行きたい場所を3箇所選べる（本当の受け入れ基準）**

# 第III部　作業指針（CLAUDE.md 相当）

## このプロジェクトで絶対に守ること

1. **三層を混ぜない** — ESTIMATE / ACTUAL / LEGAL / FIELD。異なる層の値を掛け合わせて単一の数値を作らない。事業として越えてはいけない一線。
2. **合成した総合スコアを持たない** — 軸ごとに素の値を保持。UIで重みを動かすのは可、結果をデータに書き戻さない。
3. **すべての指標に limitations を持たせる** — 空にしない。書けないなら指標を作らない。
4. **断定を出力しない** — 「有望」「買うべき」「安全」「おすすめ」を使わない。
5. **説明可能性を保つ** — 機械学習は使わない。`rules/*.yaml` から演繹し追跡可能に。

## 実装上の約束

- Python 3.11+ / 生データはコミットしない / 取得したら `data/SOURCES.md` に追記 / 乱数を使わない / 規則(YAML)とコードを分離。

## 進め方

第II部 §8 のフェーズ順。**P2（温泉宿1業種が地図に出る）までを最優先**で完成させ、そこで一度手を止める。

## 迷ったときの判断基準

**「この出力を見た人が、推定を事実と誤解する余地があるか」を問う。あるなら、その実装は採らない。**
